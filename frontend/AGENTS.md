# frontend 开发协作规范

## 适用范围

本文件适用于 `frontend/` 目录下的所有前端代码、测试、静态资源和工程配置。后续使用大模型修改前端时，优先遵守本文档；如果本文档与更深层目录中的 `AGENTS.md` 冲突，以更深层目录文档为准。

## 项目概览

已确认：

- `frontend` 是 Two-To 的 Web 前端工程目录。
- 项目产品方向是宠物适配匹配、品种解析、宠物档案、健康照料、日常管理与成长记录。
- 根 README 约定前端技术方向为 Vite + React + TypeScript + React Router + TanStack Query，Web 端优先。
- 当前已存在 `package.json`、Vite 配置、React 入口、路由、全局布局、后端 ping 联通检测和 slogan 展示入口。

推断：

- 前端会围绕“相遇与相知”和“相守与照料”两段用户旅程建设页面与功能模块。
- 当前分层设计目标是 Feature-Sliced 风格的轻量变体：应用入口、页面、功能模块、领域实体、共享能力逐层依赖。

## 协作与需求确认规则

本项目是个人项目，很多产品想法、技术文档或代码调整会以一句话或一小段描述出现。大模型协作开发时，不能把这类描述直接当作完整规格执行。

要求：

- 执行任何前端代码修改前，必须先说明准备如何改、涉及哪些文件、预期效果和主要风险，等用户明确同意后再落地。
- 如果用户已经明确说“直接改”“开整”“按这个做”等，可视为对当前已说明范围的同意；一旦发现新增范围、交互歧义或实现风险，需要再次停下来确认。
- 遇到功能目标、用户场景、交互路径、文案语气、视觉风格、接口语义等不确定点时，先提出具体问题和可选方案，不要自行脑补后继续实现。
- 涉及需求相关内容时，需要主动和用户讨论目标用户、核心场景、边界条件、优先级和可能取舍；不要简单按字面照单执行。
- 前端实现允许为提升功能完整性、交互质量、可维护性或性能引入新的技术栈或依赖；引入前需要说明它解决的问题、收益、代价、替代方案和对项目复杂度的影响。存在多个合适选择时，应给出优缺点和推荐方案，由用户选择后再落地。
- 用户不要求专业术语描述，沟通时优先使用清楚的中文解释方案、差异和影响。

## 视觉设计基调

前端页面由大模型承担 UI/UX 方案设计责任。用户不熟悉前端、UI 和交互规范时，不能把设计决策反推给用户；需要结合 `frontend-design` 的方法主动给出可执行方案：先理解产品主题、用户任务和页面职责，再定义信息层级、核心动作、空态/加载/错误态、移动端布局和色彩使用。

Two-To 的整体设计方向统一定义为：**温柔的双向适配档案系统**。

这个方向的含义：

- Two-To 不是普通萌宠展示页，也不是宠物医疗后台；它服务“认识自己、认识宠物、双向适配、建立档案、长期陪伴”这条路径。
- 页面要有温度，但不能幼稚；要能给判断，但不能冰冷；要有记录感，但不能做成沉重表格。
- 后续新增页面必须兼容当前 UI 底盘，逐步增强 Two-To 自己的识别度，不要推翻已有登录页、表单、导航和卡片基础。

### 设计兼容策略

新增页面和重构页面必须按三层处理视觉：

```text
不可变底盘：颜色、圆角、控件高度、边框、阴影、文案语气、移动端可用性
可变表达：插画强度、页面结构、业务信息密度、动效、局部排版
业务标识：H-Code / P-Code、双轨适配、档案卡、照护时间线、风险提示
```

要求：

- 现有奶白背景、暖黄主按钮、桃粉焦点态、深棕文字、浅杏边框、8px 圆角继续作为默认视觉底盘。
- 登录页和认证页可以保留更强的品牌舞台；业务页面以信息结构和业务符号建立识别度，避免每页都堆大型插画。
- 旧页面不强制一次性推倒重做；后续改动时逐步迁移到本文档规则。
- 当前首页如果重构，应优先从“口号 banner + 即将开放卡片”调整为“两段旅程 + 当前主行动”的产品路径结构。

### 颜色规则

默认设计 token 方向如下。实际 CSS 变量命名可以沿用当前项目已有变量，但新增颜色必须能映射到下列角色。

```text
Paper Milk      #FFF7EC  页面底色，温暖但不发黄
Archive White   #FFFDF8  表单、卡片、记录底色
Ink Brown       #33231A  主文字和重要标题
Muted Brown     #7A5A4A  次级说明文字
Line Apricot    #F1D4B7  边框、分隔线
Companion Amber #F6B13D  主行动、重点状态、进度高亮
Bond Rose       #E95D87  焦点态、情感强调、品牌记忆点
Habitat Sage    #6FA889  健康、稳定、已完成
Signal Blue     #4E7C9C  信息、解释、知识内容
Risk Red        #B42318  错误、风险、危险操作
```

使用要求：

- 页面不可被单一黄色、粉色、奶白或棕色统治；每个完整页面至少要有一个功能性辅助色承担真实语义，例如健康、信息、风险或完成状态。
- 不使用无语义的大面积渐变、光斑、漂浮装饰。渐变只能用于品牌首屏、登录舞台或明确的状态强调。
- 风险、冲突、不建议选择、医疗提醒等信息必须使用明确的风险色和文字说明，不能只靠温柔语气弱化。
- 品种、测评、档案、健康等长期使用页面应优先使用安静底色和清晰分区，避免高饱和背景影响阅读。

### 字体与排版

字体职责：

- 品牌大标题、登录页主视觉、重要结果标题可以使用中文 serif 或准手写感字体方向，例如 `Noto Serif SC`、`Songti SC`、`LXGW WenKai`，但必须少量使用。
- 正文、表单、列表、设置页默认使用系统无衬线字体，优先保证清晰、稳定、跨设备可用。
- H-Code、P-Code、评分、日期、提醒周期等结构化数据使用 `ui-monospace` 或等宽字体，让编码体系成为产品视觉语言。

排版要求：

- 不用负 letter-spacing；中文标题不要为了“高级感”压缩字距。
- 页面标题要直接说明当前任务，例如“适配测评”“宠物档案”“账号安全”，不要用空泛情绪标题替代功能标题。
- 结构性编号只有在真实顺序存在时使用，例如测评步骤、找回密码步骤、照护时间线；普通卡片列表不要随意写 `01 / 02 / 03`。
- 长期记录页的信息密度可以高于营销页，但必须通过分区、标签、时间线和状态色保证可扫读。

### 核心视觉符号

Two-To 后续页面优先沉淀以下业务符号，而不是新增无关装饰：

- **双轨适配**：一侧展示用户 H-Code，一侧展示宠物或品种 P-Code，中间展示匹配结论、匹配原因、潜在冲突和准备建议。
- **档案卡**：宠物基础信息、品种知识、健康记录、行为观察都用“可长期归档”的条目结构，强调来源、时间、状态和下一步。
- **照护时间线**：疫苗、驱虫、用药、就诊、体重、成长节点使用时间线或分组记录表达长期陪伴。
- **风险提示带**：不适合、潜在冲突、健康风险、行为风险必须以清晰提示区呈现，包含原因和可执行建议。
- **动物陪伴舞台**：主要用于登录、注册、空态、完成态和少数品牌首屏；业务页面只使用小型动物标记或头像，不把动物插画作为普通装饰铺满页面。

### 页面模板

新增页面必须先判断自己属于哪类模板，再开始设计和实现。

认证页：

- 结构：品牌舞台 + 表单面板。
- 用途：登录、注册、找回密码、完善资料。
- 规则：允许强品牌表达；移动端必须让表单尽早进入首屏，品牌图不能压过核心操作。

首页 / 工作台：

- 结构：当前主行动 + “相遇与相知 / 相守与照料”两段旅程入口 + 最近记录或待办。
- 规则：不要只做口号和功能卡片；至少给用户一个明确下一步，例如开始测评、建立宠物档案、查看提醒。

测评页：

- 结构：步骤进度 + 当前问题 + 选项卡片 + 解释性辅助文案。
- 规则：选项文案必须帮助用户判断真实生活条件，不做心理测试式神秘表达。

测评结果页：

- 结构：H-Code / P-Code 双轨适配 + 匹配结论 + 匹配原因 + 潜在冲突 + 养前准备 + 替代选择。
- 规则：这是 Two-To 的核心识别页面，必须优先展示解释和风险，不只展示分数或排行榜。

品种解析页：

- 结构：图鉴头部 + 品种 P-Code + 习性特征 + 照护难度 + 成本/健康/环境要求 + 适配人群。
- 规则：不要做百科长文墙；每个模块都要回答“真实养起来意味着什么”。

宠物档案页：

- 结构：宠物身份头部 + 个体 P-Code 或性格标签 + 基础信息 + 健康记录 + 行为观察 + 成长时间线 + 提醒。
- 规则：像一份长期陪伴档案，不像后台资料表；重要状态和下一次行动要明显。

健康照料页：

- 结构：即将到期提醒 + 已完成记录 + 周期计划 + 风险或异常提示。
- 规则：健康信息必须清楚、可信、克制；不能用可爱语气弱化医疗和照护风险，也不能暗示替代兽医判断。

设置 / 账号安全页：

- 结构：安静分区 + 表单控件 + 明确危险操作。
- 规则：少插画、少动效，优先可信和可控。

### 组件规则

通用组件必须延续当前 UI 底盘：

- 卡片、输入框、按钮、弹窗默认 8px 圆角。
- 表单控件高度优先使用 44px 或 48px；移动端触控目标不小于 44px。
- 卡片只用于独立信息单元、表单面板、弹窗和可重复条目；不要把页面大区块都做成漂浮卡片，也不要卡片套卡片。
- 阴影只用于需要从背景中抬起的面板或浮层；普通列表和档案条目优先用边框、分隔线和背景区分。
- 图标优先使用 `lucide-react`，按钮中的常见动作使用图标辅助识别；不要手写和现有图标库风格不一致的 SVG。
- 状态标签必须有明确语义，例如“待完成”“已完成”“有风险”“建议补充”，不要只写“推荐”“热门”这类泛化营销标签。

### 文案规则

Two-To 的文案要温柔，但必须清楚。

允许：

- “更适合你当前生活节奏的方向”
- “这里可能有冲突，需要提前准备”
- “如果仍然想选择它，建议先补齐这些条件”
- “下一次驱虫建议在 2026-07-20 前完成”

避免：

- “完美适合你”
- “最佳宠物推荐”
- “治愈你的生活”
- “一键解决养宠问题”

错误、空态和风险提示要求：

- 错误说明发生了什么，以及用户下一步能做什么。
- 空态要给明确行动入口，例如“建立第一份宠物档案”“开始适配测评”。
- 风险提示不能只说“不建议”，必须解释原因和可补齐条件。
- 登录、账号、安全、健康相关文案保持克制，不用拟人化动物语气承载关键错误。

### 动效与可访问性

- 动效只服务理解和反馈，例如登录动物回避密码、测评步骤切换、记录保存成功、提醒完成状态变化。
- 不做散乱的页面滚动动画、持续晃动装饰或影响阅读的循环动效。
- 必须尊重 `prefers-reduced-motion`；减少动态效果时关闭位移、缩放、长时间闪烁，仅保留必要状态变化。
- 所有交互控件必须有可见焦点态；颜色不能作为唯一状态表达。
- 移动端必须检查底部导航、固定按钮、弹窗和键盘弹起时是否遮挡内容。

### 新页面设计检查清单

开始实现任何新页面前，先用中文说明：

1. 页面属于哪个模板，核心用户任务是什么。
2. 页面主行动是什么，次级行动是什么。
3. 是否需要 H-Code / P-Code、档案卡、照护时间线或风险提示。
4. 加载、空态、错误态、成功态分别如何展示。
5. 桌面端和移动端结构如何变化。
6. 是否使用动物视觉；如果使用，说明它承担的语义，不允许只做装饰。
7. 是否兼容当前颜色、圆角、控件和导航底盘。

## 整体架构

当前目录结构：

```text
frontend/
  public/               # 静态资源，构建时原样输出
  src/
    app/                # 应用初始化、路由、全局 Provider、全局布局
    pages/              # 路由页面，负责组装 feature 和 entity 展示
    features/           # 具体业务功能，例如适配测评、品种检索、宠物档案编辑
    entities/           # 领域实体，例如 user、pet、breed、assessment
    shared/
      api/              # 请求客户端、接口封装、错误处理
      config/           # 前端环境配置、常量配置
      lib/              # 通用工具函数、hooks、格式化逻辑
      proto/            # 由 backend/proto/ 生成的 TypeScript 请求/响应类型
      styles/           # 全局样式、主题变量、设计 token
      ui/               # 通用 UI 组件，例如 Button、Modal、FormItem
    assets/             # 图片、字体、图标等源码资产
  tests/                # 前端测试与测试工具
```

推荐依赖方向：

```text
app -> pages -> features -> entities -> shared
```

禁止反向依赖：

- `shared` 不依赖 `entities`、`features`、`pages`、`app`。
- `entities` 不依赖 `features`、`pages`、`app`。
- `features` 不直接依赖 `pages` 或 `app`。
- 不相关的 `features` 之间不直接互相调用；确实需要复用时，优先下沉到 `entities` 或 `shared`。

## 分层职责

### app

`src/app` 是应用装配层，负责 React 根节点、路由、全局 Provider、全局布局、错误边界和页面级 loading。

要求：

- 不写具体业务规则。
- 不直接拼接口请求参数。
- 不直接处理某个业务模块的数据转换。
- 后续如果引入状态管理、请求缓存、主题系统，统一从这一层接入。

### pages

`src/pages` 是路由页面层，负责组织页面布局并组合多个 `features` 或 `entities` 展示。

要求：

- 可以读取路由参数、设置页面标题、控制页面级 loading/empty/error 状态。
- 不沉淀复杂业务规则；复杂流程下放到 `features`。
- 不直接操作底层请求客户端；接口动作优先由对应 `feature` 或 `entity` 承接。

### features

`src/features` 是功能模块层，承载明确的用户动作或业务流程。

适合放置：

- 适配性测评提交与结果展示。
- 品种筛选、检索、收藏等动作。
- 宠物档案创建、编辑、删除确认等流程。
- 健康提醒创建、完成、列表筛选等流程。

要求：

- 可以依赖 `entities` 的领域类型、展示组件和基础逻辑。
- 可以依赖 `shared/api`、`shared/lib`、`shared/ui`。
- 不把无业务语义的通用组件长期留在 feature 内；确认多处复用后再下沉。

### entities

`src/entities` 是领域实体层，沉淀稳定业务对象及其基础展示能力。

适合放置：

- `pet`、`breed`、`user`、`assessment` 等领域对象。
- 多个功能都会使用的领域类型、基础展示组件、简单领域转换。
- 与领域强相关但不绑定某个页面动作的工具逻辑。

要求：

- 不依赖具体页面或功能流程。
- 不持有页面级状态。
- 不直接处理路由跳转。

### shared

`src/shared` 是共享基础层，只放与具体业务无关或弱相关的能力。

目录职责：

- `shared/api`：HTTP client、请求拦截、错误归一化、基础请求类型。
- `shared/config`：环境变量读取、路由常量、运行配置。
- `shared/lib`：通用 hooks、日期格式化、校验、轻量工具。
- `shared/proto`：从 `backend/proto/` 生成的 TypeScript 类型，不手写生成物。
- `shared/styles`：全局样式、主题变量、设计 token。
- `shared/ui`：无业务语义的基础 UI 组件。

要求：

- `shared/proto` 的源头是 `backend/proto/*.proto`，不要直接修改生成后的类型文件。
- `shared/ui` 不出现宠物、测评、品种等具体业务概念。
- `shared/lib` 不为一两行重复逻辑随意增加 helper。

## 核心调用链路

页面渲染链路：

```text
app 初始化
  -> pages 路由页面
    -> features 业务动作与流程
      -> entities 领域对象与展示能力
      -> shared/api 发起请求
        -> shared/proto 约束请求参数与返回值类型
```

新增接口联调链路：

```text
backend/proto/*.proto
  -> 后续生成 frontend/src/shared/proto/*.ts
    -> shared/api 定义请求方法
      -> features 调用请求方法并处理业务状态
        -> pages 组合页面展示
```

当前现实：

- `shared/proto/README.md` 已明确 TypeScript 生成工具尚未接入。
- 已接入 React Router 管理页面路由。

## 数据与模型设计

已确认：

- 前后端请求参数和返回值优先由 `backend/proto/` 统一定义。
- 前端生成类型目标目录是 `src/shared/proto`。

约定：

- 页面私有 UI 状态放在页面或 feature 内，不上升到领域层。
- 业务对象类型优先贴近使用场景；跨 feature 复用后再沉淀到 `entities`。
- API 入参和出参优先引用 `shared/proto` 的生成类型，避免前后端重复手写 DTO。
- 展示模型如果与后端响应不一致，可以在 feature 或 entity 内做明确转换，并用中文注释说明转换原因。

## 注释规范

新增或修改代码时必须补充必要中文注释。

要求：

- 方法、函数、复杂 hooks、复杂组件需要说明作用。
- 请求参数和返回值需要说明业务意义，尤其是 ID、状态、枚举、时间字段和分页字段。
- 对复杂流程写“大步骤”注释，不做逐行翻译式注释。
- 对兼容逻辑、兜底逻辑、异常分支要写清楚原因。
- 生成物不补手写注释；应修改源文件或生成脚本。

TypeScript 建议格式：

```ts
/**
 * 提交宠物适配测评答案，并返回本次测评的推荐结果。
 * @param payload 测评答案与用户基础偏好，字段来自 proto 生成类型。
 * @returns 后端计算后的推荐结果与解释文案。
 */
```

## 日志与排查规范

前端日志同样重要，但要避免泄露隐私数据。

关键位置需要有可排查信息：

- API 请求失败、超时、重试和降级。
- 登录态变化、权限拒绝、会话过期。
- 重要表单提交失败。
- 复杂 feature 的关键步骤切换。
- Error Boundary 捕获到页面级异常。

要求：

- 日志中包含模块名、动作名、关键业务 ID、错误码和错误摘要。
- 不打印完整手机号、token、地址、详细病历、备注等敏感内容。
- 浏览器端日志不能替代用户可见的错误状态；页面仍需展示明确的失败、空态或重试入口。
- 后续如果接入埋点或前端日志平台，需要把日志封装放在 `shared/lib` 或 `shared/api` 的基础层，但不要为了少量调用过早抽象。

## 封装与模块拆分原则

不要过度封装。

具体要求：

- 不因为一两行逻辑重复就抽 helper。
- 不把阅读时需要连续理解的业务流程拆成大量跳转函数。
- 只有在多处复用、命名清晰、能减少真实复杂度时，才下沉到 `shared/lib` 或 `entities`。
- UI 组件先就近放置；确认无业务语义且多处复用后，再移动到 `shared/ui`。
- 请求封装先贴近 feature；多个模块复用同一资源时，再考虑沉淀到 `entities` 或 `shared/api`。

## 增量修改与兼容要求

修改已有逻辑时，优先增量演进，不要一刀切删除。

要求：

- 旧逻辑如果需要替换，先注释保留，并写明“待验证后删除”或“兼容旧流程”。
- 新逻辑放在旧逻辑附近，便于 code review 对照差异。
- 对用户可见行为、接口参数、路由路径、数据结构的修改，要在注释或文档中说明兼容影响。
- 确认旧逻辑无调用、无兼容价值后，再单独提交清理改动。

## 开发建议

新增页面：

1. 在 `pages` 建页面入口。
2. 将页面动作拆到对应 `features`。
3. 将跨功能复用的业务对象放到 `entities`。
4. 将无业务语义的基础能力放到 `shared`。

新增接口：

1. 先在 `backend/proto/` 定义请求和响应。
2. 生成前端 TypeScript 类型到 `src/shared/proto`。
3. 在 feature 内实现请求调用和业务状态处理。
4. 多模块复用后再下沉 API 封装。

排查问题：

- 先看页面层是否正确传递路由参数。
- 再看 feature 是否正确处理 loading、empty、error、success 状态。
- 再看 `shared/api` 的请求参数、响应转换和错误归一化。
- 最后对齐后端 proto 与实际接口实现。

## 提交编号规则

前端提交编号独立计数，统一使用 `taro-xxxx` 格式，`xxxx` 为四位数字。

要求：

- 严格执行：只要一次提交包含 `frontend/` 下的任何文件，提交信息必须使用 `taro-xxxx` 前缀，不允许用 `feat:`、`fix:`、`docs:`、`chore:` 等格式替代。
- 当用户要求“提交代码”“帮我 commit”“提交这些改动”等操作时，必须主动套用本规则，不要等待用户再次提醒。
- 提交前必须执行下方推荐命令查看最近一次前端编号；如果历史中存在未编号的前端提交，仍以最近一次已编号的 `taro-xxxx` 为基准递增。
- 从本次提交开始，如果历史提交中没有前端编号，则第一条前端提交使用 `taro-0001`。
- 每次提交前，先查看历史提交中最近一次前端编号，再将编号加 1。
- 提交信息必须以编号开头，格式为 `taro-0001 中文提交描述`。
- 不复用已经出现过的编号，不跳号，数字不足四位时左侧补 `0`。
- 如果一次改动同时包含前端和后端，优先拆成两次提交，前端提交使用 `taro-xxxx`，后端提交使用 `tutu-xxxx`，两边分别计数。

查看前端最近编号的推荐命令：

```bash
git log --format=%s -- frontend | rg '^taro-[0-9]{4}' | head -1
```
