# 登录与注册账号体系技术方案

## 1. 背景与目标

Two-To 当前已有前后端基础骨架，但没有账号体系。登录与注册能力会成为后续适配测评、宠物档案、健康照料、成长记录等用户数据的归属基础。

本方案目标：

- 支持全站强登录。
- 支持邮箱注册、邮箱密码登录、手机号验证码登录注册一体。
- 支持图片验证码、短信验证码、邮箱验证码、找回密码。
- 支持 access token + refresh token 登录态。
- 支持账号与安全中心，包括邮箱/手机号绑定、修改密码、设备管理。
- 支持阿里云和火山云短信供应商配置。
- 支持 SMTP 邮箱验证码。
- 引入 Redis 承载验证码、频控、登录失败计数、短期凭证和 session 有效性缓存。
- 保持当前后端分层：`routers -> controllers -> models/page -> models/data -> models/dao`。
- 保持当前前端分层：`app -> pages -> features -> entities -> shared`。

## 2. 总体架构

```text
Web 前端
  -> shared/api auth/account 请求封装
  -> 后端 /api/v1/auth、/api/v1/account
  -> controllers 解析请求
  -> models/page 执行业务流程、鉴权和风控
  -> models/data 封装事务和数据访问
  -> models/dao 映射 user/session/code 等表
  -> library/auth、verification、sms、email、cache 提供基础能力
```

## 3. 数据模型设计

### 3.0 通用字段与命名约定

所有业务表统一包含以下通用字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| status | tinyint | 状态字段，具体枚举由各表定义 |
| create_time | bigint | 创建时间，Unix 秒 |
| update_time | bigint | 更新时间，Unix 秒 |

时间字段命名统一使用 `_time` 结尾，不使用 `_at` 结尾。例如：

- `create_time`
- `update_time`
- `expire_time`
- `verify_time`
- `use_time`
- `revoke_time`
- `last_active_time`

不单独设计 `deleted_at` 或 `delete_time` 字段。删除视为一次状态更新，通过 `status` 表达删除、失效、作废等状态，通过 `update_time` 表达最后一次状态变化时间。

DAO 层建议提取通用结构体：

```go
type BaseModel struct {
    Status     int32 `gorm:"column:status" json:"status"`
    CreateTime int64 `gorm:"column:create_time" json:"createTime"`
    UpdateTime int64 `gorm:"column:update_time" json:"updateTime"`
}
```

各表 DAO 结构体通过嵌入 `BaseModel` 复用通用字段。每张表根据自身业务定义 status 枚举，例如用户表的 `status` 表示账号状态，验证码表的 `status` 表示验证码状态，会话表的 `status` 表示会话状态。

### 3.1 users

用户主表，只存用户稳定身份和状态，不直接把邮箱/手机号耦合在主表上。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint unsigned | 用户 ID |
| nickname | varchar(64) | 昵称，允许重复 |
| status | tinyint | 账号状态：1 正常，2 临时锁定，3 禁用 |
| password_hash | varchar(255) | 密码哈希；手机号验证码注册后可为空，设置密码后写入 |
| password_update_time | bigint | 密码更新时间，Unix 秒 |
| create_time | bigint | 创建时间，Unix 秒 |
| update_time | bigint | 更新时间，Unix 秒 |

索引：

- 主键：`id`
- 普通索引：`idx_status`

### 3.2 user_auth_identities

账号登录身份表，统一管理邮箱和手机号绑定。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | bigint unsigned | 主键 |
| user_id | bigint unsigned | 用户 ID |
| identity_type | tinyint | 身份类型：1 邮箱，2 手机号 |
| identity_value | varchar(128) | 标准化后的邮箱或手机号；状态正常时必填，解绑后置空 |
| status | tinyint | 绑定状态：1 正常，2 已解绑 |
| verify_time | bigint | 验证通过时间 |
| create_time | bigint | 创建时间 |
| update_time | bigint | 更新时间 |

索引：

- 唯一索引：`uk_identity_type_value(identity_type, identity_value)`
- 普通索引：`idx_user_id(user_id)`

说明：

- 邮箱统一转小写并去除前后空格。
- 手机号统一存 `+86` + 11 位手机号，例如 `+8613800000000`。
- 同一用户必须至少保留一种 `status=1` 的联系方式。
- 解绑邮箱或手机号时，将该行 `status` 更新为已解绑，并清空 `identity_value`，避免历史解绑记录阻塞同一联系方式后续重新绑定。
- 解绑前后的脱敏信息写入 `security_logs`，身份表只保留当前可用绑定关系。

## 4. 接口设计

### 4.1 Auth 接口

#### GET /api/v1/auth/captcha

生成图片验证码。

响应：

- `captchaId`：图片验证码 ID。
- `imageBase64`：验证码图片 base64。
- `expiresIn`：有效秒数。

#### POST /api/v1/auth/send-code

发送短信或邮箱验证码。

请求：

- `codeType`：sms / email。
- `scene`：login / register / forgot_password / bind_phone / bind_email。
- `target`：手机号或邮箱。
- `captchaId`：图片验证码 ID。
- `captchaCode`：图片验证码。

响应：

- `cooldownSeconds`：下次可发送等待秒数。
- `expiresIn`：验证码有效秒数。

#### POST /api/v1/auth/email-login

邮箱密码登录。

请求：

- `email`
- `password`
- `captchaId`：触发风控后必填。
- `captchaCode`：触发风控后必填。

响应：

- `accessToken`
- `accessTokenExpiresIn`
- `refreshToken`
- `refreshTokenExpiresIn`
- `user`

#### POST /api/v1/auth/phone-login

手机号验证码登录注册一体。

请求：

- `phone`
- `smsCode`

响应：

- 已有账号：返回 token 和 user。
- 新手机号：返回 `profileSetupToken`，前端进入完善基础资料。

#### POST /api/v1/auth/email-register/verify

校验邮箱注册验证码。

请求：

- `email`
- `password`
- `emailCode`

响应：

- `profileSetupToken`

说明：

- 该接口只校验邮箱、密码和验证码，不创建账号。
- 账号在完善基础资料提交后创建。

#### POST /api/v1/auth/complete-profile

完善基础资料并创建账号。

请求：

- `profileSetupToken`
- `nickname`
- `petStage`
- `interestedPetTypes`
- `petExperience`
- `dailyCompanyTime`
- `livingSituation`
- `petConstraints`

响应：

- `accessToken`
- `accessTokenExpiresIn`
- `refreshToken`
- `refreshTokenExpiresIn`
- `user`

#### POST /api/v1/auth/refresh

刷新登录态。

请求：

- `refreshToken`

响应：

- `accessToken`
- `accessTokenExpiresIn`
- `refreshToken`
- `refreshTokenExpiresIn`

说明：

- refresh token 每次刷新后轮换。
- 重复使用旧 refresh token 视为异常会话，记录安全日志。

#### POST /api/v1/auth/logout

退出当前设备。

请求：

- `refreshToken`

响应：

- 空数据。

### 4.2 找回密码接口

#### POST /api/v1/auth/forgot-password/verify-code

校验找回密码验证码。

请求：

- `identityType`：email / phone。
- `identityValue`
- `code`

响应：

- `resetToken`

说明：

- 不暴露账号是否存在。
- 只有验证码匹配且账号存在时返回有效 reset token。

#### POST /api/v1/auth/forgot-password/reset

重置密码。

请求：

- `resetToken`
- `newPassword`

响应：

- 空数据。

说明：

- 重置成功后该用户所有 refresh token 失效。

以下接口均要求登录态。

#### GET /api/v1/account/me

获取当前用户信息。

响应：

- `user`
- `profile`
- `identities`

#### PATCH /api/v1/account/profile

修改基础资料。

请求：

- `nickname`
- `petStage`
- `interestedPetTypes`
- `petExperience`
- `dailyCompanyTime`
- `livingSituation`
- `petConstraints`

#### PUT /api/v1/account/security/email

绑定或修改邮箱。

请求：

- `email`
- `emailCode`

#### PUT /api/v1/account/security/phone

绑定或修改手机号。

请求：

- `phone`
- `smsCode`

#### DELETE /api/v1/account/security/email

解绑邮箱。

请求：

- `currentPassword`

规则：

- 账号必须保留至少一种联系方式。

#### DELETE /api/v1/account/security/phone

解绑手机号。

请求：

- `currentPassword`

规则：

- 账号必须保留至少一种联系方式。

#### PUT /api/v1/account/security/password

修改密码。

请求：

- `currentPassword`
- `newPassword`

规则：

- 修改成功后，除当前设备外的其他 refresh token 失效。

#### GET /api/v1/account/sessions

查询登录设备列表。

响应：

- `sessions`
- `currentSessionId`

#### DELETE /api/v1/account/sessions/:sessionId

踢出指定设备。

规则：

- 只能踢出当前用户自己的设备。
- 当前设备退出使用 `/auth/logout`。

#### POST /api/v1/account/sessions/revoke-all

退出全部设备。

请求：

- `currentPassword`

规则：

- 使当前用户所有 refresh token 失效。
- 前端操作完成后跳转登录页。

## 7. 后端实现细节

### 7.1 密码

- 使用 `bcrypt` 或 `argon2id` 做密码哈希。
- 不保存明文密码。
- 密码规则：8-64 位，允许字母、数字、符号；禁止纯空格、常见弱密码、与邮箱/手机号明显相同。
- 登录错误统一提示“账号或密码不正确”。

### 7.2 Token

- access token 有效期 15 分钟。
- refresh token 有效期 30 天。
- access token 可以使用 JWT。
- refresh token 使用高强度随机字符串，服务端只保存摘要。
- refresh token 每次刷新后轮换。
- 被踢出设备时，目标 session 的 `status` 更新为已踢出，`revoke_time` 写入当前时间。

#### 7.2.1 Session 存储：MySQL 与 Redis 分工

token 本身分两类：

- access token：短有效期，适合做无状态 JWT，服务端不必逐条存储。
- refresh token / 设备会话：需要支持刷新、踢出设备、退出全部设备、复用检测和审计，因此必须有服务端存储。

本期明确引入 Redis，但 Redis 不替代 MySQL 的会话事实表。两者分工如下。

MySQL 保存用户会话的事实记录：

- 需要在账号与安全页展示设备列表。
- 需要保留最近活跃时间、失效原因、安全审计信息。
- 需要支持用户主动踢出设备和退出全部设备。

Redis 保存高频、短生命周期、天然过期的数据：

- session 有效性缓存，例如 `session:{session_id}`。
- refresh token 轮换锁，避免并发刷新导致重复 token 状态混乱。
- 验证码发送频控计数，例如按手机号、邮箱、IP、场景维度计数。
- 登录失败短期计数和临时锁定。
- 找回密码、完善资料等短期凭证。
- access token 黑名单，如后续需要让短期 token 立即失效。

本期方案：

- 以 MySQL 作为 session 的事实源，保证设备管理和审计能力稳定可查。
- 以 Redis 作为验证码、频控、登录失败计数、短期凭证和 session 有效性缓存。
- 登录、刷新 token、踢出设备等关键操作先更新 MySQL，再更新或删除 Redis 缓存。
- 读取会话状态时优先查 Redis；Redis 未命中时回源 MySQL，并把有效 session 回填 Redis。

Redis 不可用时的策略：

- 生产环境 Redis 不可用时，验证码发送、登录失败计数和 refresh token 刷新应返回明确失败，不静默降级，避免绕过风控。
- 普通 access token 鉴权可回源 MySQL 校验 session 状态，但需要记录 Redis 异常日志。
- 本地开发环境可使用内存 cache mock，但必须通过配置显式启用。

#### 7.2.2 Redis Key 设计

Redis key 统一使用配置项 `TWO_TO_REDIS_KEY_PREFIX` 作为前缀。示例：

```text
two-to:captcha:{captcha_id}
two-to:verify-code:{scene}:{target}
two-to:rate:code:{scene}:{target}
two-to:rate:ip:{scene}:{ip_hash}
two-to:login-fail:{identity_type}:{identity_value}:{ip_hash}
two-to:lock:login:{identity_type}:{identity_value}
two-to:session:{session_id}
two-to:refresh-lock:{session_id}
two-to:profile-setup:{token}
two-to:password-reset:{token}
```

TTL 原则：

- 图片验证码：5 分钟。
- 短信/邮箱验证码：10 分钟。
- 发送频控：按 60 秒、1 小时、1 天三个窗口分别设置 TTL。
- 登录失败计数：15 分钟到 1 小时。
- session 缓存：不超过 refresh token 剩余有效期。
- refresh lock：10-30 秒。
- profile setup / password reset token：10 分钟。

### 7.3 验证码

- 短信/邮箱验证码为 6 位数字。
- 图片验证码有效期 5 分钟。
- 短信/邮箱验证码有效期 10 分钟。
- 验证码成功使用后立即失效。
- 同一目标同一用途 60 秒内不能重复发送。
- 同一目标同一用途 1 小时最多 5 次，1 天最多 10 次。
- 同一 IP 1 小时最多触发 30 次验证码发送。
- 验证码明文和频控计数存 Redis。
- MySQL 的 `verification_codes` 表保存验证码摘要、发送结果和安全审计记录，不作为高频校验主路径。

### 7.4 短信供应商

抽象接口：

```go
type Sender interface {
    SendVerificationCode(ctx context.Context, phone string, code string) error
}
```

错误归一：

- `RetryableProviderError`：可重试通道异常，可切换备用供应商。
- `BusinessProviderError`：不可重试业务失败，例如模板未审核、手机号非法、频控命中。
- `ConfigProviderError`：配置错误，例如密钥缺失、签名错误。

主备策略：

- 主供应商出现可重试通道异常时，尝试备用供应商。
- 不可重试业务失败和配置错误不自动切换。
- 所有供应商失败后，用户侧展示“验证码发送失败，请稍后重试”。

### 7.5 邮件发送

- 使用 SMTP 发送纯文本验证码邮件。
- 邮件主题：`Two-To 验证码`。
- 发件人名称：`Two-To`。
- SMTP 错误只记录摘要，不暴露给用户。

### 7.6 鉴权中间件

新增 `middlewares.Auth()`：

- 读取 `Authorization: Bearer {accessToken}`。
- 校验 token 签名和过期时间。
- 注入当前 `userID` 和 `sessionID` 到请求上下文。
- 失败时返回 HTTP 401，业务码建议单独定义为 `40100`。

开放接口不挂鉴权中间件：

- `/api/v1/auth/*`
- `/health`
- `/api/v1/ping`
- `/api/v1/slogan`

业务接口和 `/api/v1/account/*` 挂鉴权中间件。

### 7.7 定时清理

首期做简单定时任务：

- 清理 30 天前验证码记录。
- 清理 180 天前已失效 session 记录。
- 清理过期且已失效的 reset/profile setup 临时凭证记录。

## 12. 风险与取舍

### 12.1 真实短信服务依赖

风险：签名、模板审核和密钥配置可能阻塞联调。

处理：

- 本地和测试环境保留 mock provider。
- 生产环境启动时必须检查真实短信配置。

### 12.2 refresh token 存储

风险：前端 `localStorage` 存储 refresh token 有 XSS 风险。

处理：

- 首期用该方案换取实现效率。
- 禁止前端注入未净化 HTML。
- 后续迁移 httpOnly Cookie。

### 12.3 Redis 基础设施依赖

风险：本期引入 Redis 后，本地开发、测试和部署需要额外维护 Redis 实例。

处理：

- 生产环境 Redis 不可用时，验证码发送、登录失败计数和 refresh token 刷新返回明确失败。
- 普通 access token 鉴权可回源 MySQL 校验 session 状态，但必须记录 Redis 异常日志。
- 本地开发环境建议启动本地 Redis；如果确实不方便，可以通过显式配置启用内存 cache mock。

### 12.4 全站强登录影响转化

风险：所有页面强登录可能降低新用户浏览意愿。

处理：

- 登录页保持轻量。
- 手机号验证码默认入口降低登录成本。
- 完善基础资料只强制少量字段。

### 12.5 小动物动效实现复杂度

风险：五只动物互动舞台会增加前端实现和调试成本。

处理：

- 与账号链路解耦，作为独立组件。
- 先实现静态插画和基础眼睛跟随。
- 后续逐步增加密码明文回避、成功、错误等状态。
